## Prioritized changes

### R01 / P1 — Make shared confirmation dialogs truly modal

Confirmed independent observation, root-assisted IAB, isolated synthetic preview5179/API58004. Finance Manager opened Vendors → Vendor Administration → Sample OfficeWorks Trading → Deactivate. With Cancel focused, Shift+Tab moved focus to a background Delete button (`closest('[role=dialog]')` false); the screenshot showed its focus ring behind the open confirmation. Escape then closed the confirmation, but activeElement became BODY rather than the Deactivate invoker. No record was deactivated or deleted in this manual pass.

`src/prototype.js:787–826` renders a section with role=dialog/aria-modal and focuses the first select/input, but does not contain Tab focus or restore its invoker. The global Escape handler around5471 closes the prompt; therefore missing Escape is **not** the finding. A visual overlay/aria-modal alone does not implement keyboard modality. Background destructive controls must not remain reachable while confirmation is open.

Recommend reusing the boilerplate's native `<dialog>.showModal()` behavior or an equivalent centralized, tested dialog controller with inert background, Tab/Shift+Tab containment, initial focus and explicit opener restoration. Handle nested document-review prompts over vendor details without leaving two interactive modal layers. Preserve reason/destination and busy/error states across asynchronous app updates. Keep request permissions/approval policy on the server.

Code impact: medium, shared confirmation presentation/event binding, potentially shared shell styles. Retest return/decline, override, vendor deactivate/delete and nested supplier-document correction; verify keyboard wrap and restored invoker, not only successful API output. This fix would address a confirmed defect, but is not yet evidence that it fixes QA F01's disappearing reason.

### R02 / P2 — Gate the empty dashboard CTA by actual permission

Root-assisted manual Finance Manager dashboard had no records and offered Create Request, which opened the type picker. The FM navigation contains no New Request. `src/prototype.js:3352` renders that CTA unconditionally when visibleRequests is empty. `api/payment_module/seed.py` grants requests.create to Requestor, Department Head and System Administrator, not the default Finance Manager role. The backend create endpoint still enforces permission.

Recommend deriving this empty-state action from authUser.permissions: offer Create Request only with requests.create; otherwise provide a useful permitted action, such as Approval Queue or clearing active filters. This is misleading navigation/a likely dead end, **not demonstrated unauthorized request creation**. Code impact small in dashboard empty-state rendering; test both true-empty and filtered-empty lists for requestor, Finance Manager and admin.

### R03 / P2 — Align Finance setup instructions after policy confirmation

Carries forward QA F03, independently confirmed still present in current source. `src/finance-initial-setup-ui.js:15` says each payment line has one assigned signatory. Current implementation/migration0031 and status documents describe removal of the separate signatory gate; earlier user history included one-signatory approval. Do not silently change financial policy to match whichever text is easiest. Confirm the intended policy, then change either the workflow or copy accordingly.

`src/prototype.js` activation rendering also calls its action Activate saved General setup while the initial wizard tells Finance to activate All request types. Prefer the actual selected/saved scope in the action label; show consistent status/scope in one compact summary. Code impact small for label corrections if policy already matches code; larger approval/permission/history/test work if the financial policy must change.

Vendor verification displays the files and explains that directory review does not approve the request, but offers no direct Open request action/reference. Missing files should keep their explicit missing state and route to the requestor correction path rather than offer fake uploads in administration.

### R06 / P2 — Standardize and extend frontend units before adding another framework

The earlier statement that no frontend runner was configured was incomplete: there is no package script or dedicated framework, but **Node's built-in test runner already executes two frontend JavaScript test files**,8 cases. The original QA report has a dated correction. Inventory found no other non-pytest/non-spec test files beyond these two; the other tests/e2e JavaScript files are fixture/setup/flow helpers.

Immediate recommendation (not implemented): add a documented `test:unit` script using `node --test tests/*.test.js`, run it in CI alongside pytest/build/browser tests, and preserve the8 existing tests. Do not require a Vitest/React Testing Library migration merely because React dependencies/App.jsx exist: index.html loads the imperative prototype.js application.

Useful next pure-function tests:

- `status-label.js`: aliases, acronym casing, null/underscore handling without changing stored codes.
- `conversation-message.js`: escape hostile HTML, highlight only known participant mentions, punctuation/prefix/overlapping names.
- `tracker-table.js`/`tracker-status.js`: retain existing natural sort/date boundary/independent approval-payment cases; extend empty and mixed-state inputs based on actual reports.
- Extract shared prompt state/validation into a small module: required whitespace-only reason, role destination changes, no duplicate submit, reason retention across unrelated updates, error recovery. Do not test a private implementation copy rather than the production module.
- `data-source.js` response normalization via injected/mock fetch: validation-array errors,401/403/409/422, non-JSON failure, malformed success and network interruption. Avoid calling real services from unit tests.

If DOM/controller tests need a browser-like environment, then Vitest+jsdom (or Node plus a DOM library) is a reasonable optional second step after isolating event binding from global boot. Choose one test harness; avoid parallel competing runners without benefit. React Testing Library is appropriate only for real React-rendered components. DOM emulation cannot certify actual focus/inert behavior, scrolling, CSS layout, MinIO uploads, authorization or multi-role approvals: retain Playwright and real-browser checks. Add a regression that asserts focus/reason survive delayed notification/toast or data refresh; current full render/rebinding is a plausible timing contributor, not a proven root cause of QA F01.
